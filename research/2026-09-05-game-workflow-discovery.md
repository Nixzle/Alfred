## Decisions and counterevidence

| Finding | Disposition/action | Why and boundary |
|---|---|---|
| Shared visual rules, independent decoration seed, actual-size inspection | ADOPT / IMPLEMENT NOW in Archives | Useful beyond the source game; native components often suffice |
| Production-logic simulations, versioned policies, paired-seed comparisons | ADOPT / IMPLEMENT NOW in Archives | Reproducible experimental method; no claim that bots establish human difficulty |
| App-specific renderer or simulation runner | PROTOTYPE when a scoped project task needs it | Full architecture may be excessive; requires project acceptance and evidence |
| Template/reference consistency | ADOPT within visual procedure | Already overlaps shared design-system practice; no separate component |
| Generic engine rewrite, wholesale skill installation or new named spell | REJECT for this promotion | No measured benefit or necessary gap established |
| Data-Oriented Design / Steam Demo Release skill links | WATCH | Adjacent leads, not inspected/adopted here; Steam specialization is not automatically useful for mobile |

The main opposing case is that the existing design/testing guidance already covers much of this, and importing entire workflows would add overhead. The chosen change keeps only domain-specific details and links existing spells. Renderer/simulator adoption should be rejected if ordinary components or bounded engine scripts provide equivalent results at lower cost.
