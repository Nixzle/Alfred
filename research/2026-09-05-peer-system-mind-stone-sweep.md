# Peer-System Mind Stone Sweep

Date: 2026-09-05
Mode: Meta-Cerebro + Expertise Forge (Mind Stone amplification)

## Objective

Scout current peer agent operating systems, durable-memory systems, orchestration runtimes, second-brain architectures, governance frameworks, and workflow engines for mechanisms that can improve Sanctum without importing whole frameworks.

## Strong donors and mechanisms

### SecondBrain (contextosai/SecondBrain-collab)
Strongest mechanisms:
- promotion-aware knowledge flow: raw capture -> promoted knowledge -> compiled task context;
- working/episodic/long-term memory separation;
- review-queued memory distillation instead of silent durable writes;
- policy-aware action classes;
- durable sessions with checkpoints, branch/resume metadata and approval waits;
- one quality-control loop connecting traces, replay cases, evals and improvement pressure.

Disposition:
- ADOPT pattern: promotion-aware memory pipeline and review queue.
- ADOPT pattern: quality pressure loop unifying trace -> replay -> eval -> candidate improvement.
- REJECT wholesale framework adoption.

### Mainspring (fablerlabs/mainspring)
Strongest mechanisms:
- constitution enforced by code rather than prompt obedience;
- capability-gated side effects;
- persistent operation that wakes, performs bounded work, writes state, and sleeps;
- human approval queue for effects outside autonomous authority;
- accounting/ledger treated as runtime state.

Disposition:
- ADOPT principle: high-value hard rules must migrate from prose to tool/runtime gates.
- ADOPT pattern: persistent-operation slice with explicit ledger and handoff state where needed.
- Current overlap: TVA/operational-integrity roadmap already targets much of this; donor mainly strengthens implementation priority.

### NabaOS (nabaos/nabaos)
Strongest mechanisms:
- cache-first multi-tier request routing;
- cryptographically signed constitutions that agents cannot self-modify;
- provider-independent routing by cost/quality;
- process-isolation / permission-model framing.

Disposition:
- PROTOTYPE: cache-first route before expensive model/tool execution for repeated tasks.
- PROTOTYPE: signed/immutable policy artifacts for high-risk runtime boundaries.
- WATCH: broad OS abstraction; too much framework for current Sanctum.

### Lethe (openlethe/lethe)
Strongest mechanisms:
- split between session memory and versioned durable memory;
- checkpoints/interruption recovery;
- durable memory with immutable history, branching and merging.

Disposition:
- ADOPT pattern: branch/merge semantics for durable memory candidates.
- ADOPT pattern: explicit distinction between session continuity state and reviewed durable truth.
- This reinforces existing Checkpoint/Fork and Memory Maintenance promotions.

### MNEMOS (ncz-os/mnemos)
Strongest mechanisms:
- explicit memory lifecycle runtime: write, search, compress, version, reason, audit, export/import;
- replay -> cluster -> consolidate -> synthesize -> extract maintenance pipeline;
- operator-audited compression;
- right-to-be-forgotten lifecycle worker;
- recall observability and memory portability format.

Disposition:
- ADOPT pattern: staged memory maintenance pipeline.
- ADOPT pattern: recall observability so retrieval quality itself becomes inspectable.
- ADOPT principle: export/import portability for durable memory.
- WATCH: large named-subsystem implementation; avoid taxonomy inflation.

### AgentOS (framerslab/agentos)
Strongest mechanisms:
- source-confidence decay and reconsolidation;
- retrieval-induced forgetting / memory decay;
- runtime tool forging through schema + judge + sandbox.

Disposition:
- PROTOTYPE: confidence/freshness decay for time-sensitive memories.
- PROTOTYPE: sandboxed temporary tool incubation before canonical promotion.
- REJECT automatic permanent self-authored tools without separate evidence/governance.

### Open Multi-Agent (open-multi-agent/open-multi-agent)
Strongest mechanisms:
- coordinator creates runtime task DAG;
- deterministic scheduler executes the DAG;
- run remains inspectable, approvable and replayable.

Disposition:
- ADOPT pattern: planner may produce task graph, but deterministic scheduler owns graph execution.
- ADOPT pattern: run data must be replayable/inspectable rather than surviving only as agent narration.

### Solar (Uhorizon-AI/Solar)
Strongest mechanisms:
- central router with domain-local governance and memory;
- explicit delegation contracts and onboarding templates;
- context boundaries treated as primary architecture.

Disposition:
- ADOPT pattern: project/domain-local governance overlays beneath global Sanctum doctrine.
- Existing project-precedence/bootstrap rules already implement much of this; use as confirmation, not duplicate architecture.

### NOVA (noivan0/NOVA)
Strongest mechanisms:
- event-driven orchestration triggered by memory/state changes rather than polling;
- declarative harness pipelines.

Disposition:
- PROTOTYPE: event-driven wakeups for Presence/Watcher integrations when a real event source exists.
- ADOPT principle: prefer event triggers over polling when infrastructure supports reliable event delivery.

### AI Second Brain (BrianArfi/ai-second-brain)
Strongest mechanisms:
- correction -> durable lesson shortcut;
- hooks for automatic guardrails;
- shared reusable workflows and subagents;
- low-friction first-value setup.

Disposition:
- ADOPT pattern: fast correction-to-candidate path below full Failure Harvest ceremony.
- Existing Failure Harvest remains canonical for meaningful promotion.

## Candidate upgrades for Sanctum

### IMPLEMENT / strengthen now
1. **Promotion-aware memory pipeline**
   `raw/transient -> candidate -> reviewed/promoted -> compiled task context`.
2. **Recall observability**
   Watch not just stored memories but what retrieval selected, omitted, superseded or failed to surface.
3. **Replay-case quality loop**
   `Watcher failure/trace -> minimal replay case -> Web eval -> candidate doctrine/runtime change`.
4. **Deterministic DAG execution**
   LLM may plan dependencies; deterministic scheduler executes known graph semantics where practical.
5. **Hard-rule migration priority**
   Any frequently consequential prose invariant should be considered for tool/runtime enforcement.
6. **Memory branch/merge semantics**
   Durable candidate changes should support reviewable branches rather than immediate canonical overwrite.
7. **Memory portability/export**
   Durable Sanctum state should remain exportable/recoverable independently of one hosted system.

### PROTOTYPE
8. **Confidence/freshness decay** for volatile facts and capabilities.
9. **Cache-first routing** for repeat/retrieval-heavy tasks before invoking expensive reasoning.
10. **Signed policy artifacts** for high-risk execution surfaces.
11. **Sandboxed temporary tool incubation** with expiration and promotion gate.
12. **Event-driven Presence triggers** where reliable event surfaces exist.

### REJECT / avoid
- wholesale adoption of any peer framework;
- taxonomy inflation merely because another project gives every subsystem a name;
- automatic self-modification of canonical tools/doctrine;
- treating community popularity or benchmark claims as sufficient proof without local evidence.

## Key strategic finding

Sanctum is comparatively strong in orchestration doctrine, authority boundaries and explicit failure harvesting. Peer systems are strongest where Sanctum remains lighter: **mechanical memory lifecycle, enforcement at the runtime boundary, replayable execution state, retrieval observability, and low-cost routing**.

The optimal route is therefore not more members. It is to mechanically strengthen the existing knowledge, runtime, Watcher, Web, TVA and Presence planes with selected donor mechanisms.
