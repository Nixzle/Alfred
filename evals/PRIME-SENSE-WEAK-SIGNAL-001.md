# PRIME-SENSE-WEAK-SIGNAL-001

## Purpose

Regression for Prime Sense failures where no single observation is decisive, but correlated weak signals should cause a bounded investigation or attention elevation before the user manually supplies the synthesis.

## Case A — avoidable reinvention

Context:
- active project is building a substantial custom subsystem;
- prior research already identified adjacent mature donor ecosystems;
- two recent user corrections reveal omitted donor classes;
- implementation effort continues to increase.

Fail if:
- Prime Sense remains silent and execution continues greenfield;
- no Salvage First / donor check is proposed until user explicitly asks;
- user correction pattern is treated as isolated events.

Pass if:
- Prime Sense correlates the repeated donor misses;
- moves the pattern into Mindscape;
- routes a bounded donor/Meta-Cerebro check before more substantial custom work.

## Case B — peer-system blindness

Context:
- Sanctum itself is being upgraded;
- multiple new orchestration/memory capabilities are being discussed;
- known peer agent runtimes, plugin ecosystems, MCP registries and workflow engines exist.

Fail if:
- research inspects only generic papers/best practices;
- no peer-system/plugin/MCP donor sweep occurs;
- the user later supplies an obvious high-signal system such as Hermes that should have been found.

Pass if:
- Prime Sense recognizes a meta-level salvage opportunity;
- Meta-Cerebro checks peer systems and extension ecosystems;
- the donor map changes execution or explicitly records why not.

## Case C — gradual runtime drift

Context:
- tool success rate declines moderately over several runs;
- retry count and latency both rise;
- no individual run crosses a hard failure threshold.

Fail if:
- Prime Sense treats every run independently and never raises drift/change investigation.

Pass if:
- Watcher/Prime Sense correlate the metrics;
- distinguish possible drift from one-off noise;
- recommend bounded revalidation/change-point investigation without claiming certainty.

## Case D — dependency risk

Context:
- important dependency has slowing maintenance;
- a vulnerability/advisory appears;
- a compatible donor/replacement exists;
- project still depends on the old component.

Fail if:
- no attention item forms until the dependency actually breaks.

Pass if:
- dependency-risk signal forms;
- evidence is gathered from maintainer/security/current compatibility sources;
- migration/update is prepared or surfaced according to authority.

## Case E — correlated completion seams

Context:
- happy path repeatedly passes;
- reconnect, error-state and cancellation paths remain untested;
- tester feedback repeatedly mentions confusion/dead ends.

Fail if:
- feature is repeatedly described as complete based only on happy path.

Pass if:
- Prime Sense elevates completion-seam risk;
- Evidence Lock/verification scope is corrected.

## Case F — notification discipline

Context:
- ten alerts are symptoms of one underlying incident.

Fail if:
- Prime Sense emits ten independent interruptions.

Pass if:
- signals are deduplicated/correlated;
- one consolidated attention item is surfaced with severity/confidence and evidence.

## Constraint

Passing does not require continuous surveillance or autonomous consequential action. It requires recognizing and routing material signal combinations from evidence actually available in the runtime.
